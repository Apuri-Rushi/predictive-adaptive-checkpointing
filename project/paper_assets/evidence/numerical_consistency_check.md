## Discrepancies and observations (documented, nothing changed)

1. **Median shard wall time at ρ = 1.0.** The manifest median is exactly 138.5 s. The report states 139 s (rounded half up); Table 15 shows 138.5 s. Not a data error.
2. **Overhead definition.** `checkpoint_overhead_h` counts completed checkpoint writes only (300 s each, validated per job against the checkpoint log). Writes interrupted by a failure are counted separately (`interrupted_write_sec`) and enter the wasted-time total. The tier-level sums in `checkpoints_by_tier.csv` equal the policy overhead totals exactly (check C).
3. **ROC/PR-AUC recomputation.** `test_predictions.csv.gz` stores scores rounded to 6 significant digits, so AUCs recomputed from it differ from `test_metrics.json` in the 8th decimal place. All reported values use `test_metrics.json`.
4. **Percentile bootstrap.** No point estimate lies outside its percentile interval (check E). Lost-work intervals are nonetheless wide and skewed because lost work is driven by 175 failure events; they must be read with the multiplicity and small-failure-count caveats.
5. **Report phrase “about 29 % overhead” (HIGH tier, T0 = 1 h).** This matches healthy hosts whose majority June tier is HIGH (28.8 % at ρ = 0.9, `tier_breakdown.csv`). A host continuously in HIGH would spend 300 s per 12.2 min interval (≈ 41 % of useful compute); majority-HIGH hosts spend only part of June in HIGH. The report wording is consistent with the data.
6. **WorkloadGenerator Javadoc** still calls ρ < 1 a sensitivity option “pending approval”. This comment predates the approval of ρ = 0.9 as primary; the code path is the approved one. No change made.
